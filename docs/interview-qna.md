# 면접 예상 질문 & 답변 정리

> 이 프로젝트의 트러블슈팅 경험을 바탕으로 나올 만한 질문과 답변 요지입니다. 답변은 **결론 → 근거 → 내가 한 일** 순서로 정리했습니다.

---

## 네트워크 / 실시간성

### Q1. 실시간 게임인데 왜 UDP가 아니라 TCP(WebSocket)를 썼나요?

- **결론**: 브라우저 게임이라 UDP 소켓을 쓸 수 없었고, 장르상 TCP로도 충분하다고 판단했습니다.
- **근거**: 브라우저 JavaScript에는 raw UDP API가 없습니다. UDP 성격의 통신을 하려면 WebRTC DataChannel이나 WebTransport가 필요한데, 시그널링·HTTP/3 인프라가 추가로 필요합니다. 또 이 게임은 협동 타이쿤이라 **주문·서빙처럼 절대 유실되면 안 되는 이벤트**가 위치보다 중요합니다.
- **내가 한 일**: 프로토콜을 바꾸는 대신, TCP 안에서 체감 지연을 줄였습니다. 전송 주기를 약 60Hz에서 20Hz로 줄이고, 클라이언트 보간을 넣고, 서버의 Redis 쓰기를 전달 경로에서 뺐습니다.

### Q2. TCP의 어떤 특성이 게임에 불리한가요?

- **Head-of-Line Blocking**입니다. 패킷 하나가 유실되면 재전송될 때까지 **그 뒤 패킷이 모두 대기**합니다. 위치처럼 최신 값만 의미 있는 데이터에서는, 이미 의미 없어진 옛 위치 때문에 새 위치까지 늦어집니다.
- 체감상으로는 캐릭터가 **멈췄다가 몰아서 움직이는** 현상으로 나타납니다.

### Q3. 다른 플레이어의 캐릭터를 부드럽게 보이게 한 방법은?

- 받은 좌표를 바로 대입하지 않고 **목표 좌표로만 저장**한 뒤, 매 프레임 목표의 15%씩 다가가는 **선형 보간(Lerp)** 을 적용했습니다.
- **트레이드오프**: 60fps에서 계수 0.15로 남은 거리의 90%를 따라잡으려면 `ln(0.1)/ln(0.85) ≈ 14프레임 ≈ 236ms`가 걸립니다. 부드러운 대신 **표시 지연이 늘어납니다.**
- **개선 방향**: 타임스탬프 기반 스냅샷 보간(약 100ms 과거를 두 점 사이로 보간)으로 바꾸면, 지연은 일정하게 유지하면서 프레임레이트와 무관해집니다.

### Q4. 내 캐릭터는 어떻게 처리했나요?

- 서버 응답을 기다리지 않고 **입력 즉시 로컬에서 움직입니다.** 네트워크로는 50ms마다 현재 위치만 보냅니다. 내 조작 반응에는 네트워크 지연이 전혀 없습니다.

## 동시성 / 순서

### Q5. TCP는 순서를 보장하는데, 순서 문제가 생길 수 있나요?

- **네, 실제로 겪었습니다.** TCP는 네트워크 계층까지의 순서만 보장합니다. Spring STOMP는 받은 메시지를 `clientInboundChannel`의 **스레드 풀**에서 처리합니다. 그래서 같은 세션의 메시지도 병렬로 실행되어 순서가 바뀔 수 있습니다.
- 통합 테스트에서 이동 `(10,20)` → `(30,40)`을 보냈는데 `(10,20)`이 최종값으로 남는 현상을 **7회 중 5회** 재현했습니다.
- `registry.setPreserveReceiveOrder(true)`와 `config.setPreservePublishOrder(true)`로 **세션 안에서만 순서를 지키고, 세션끼리는 병렬로** 처리하게 했습니다.

### Q6. 같은 닉네임으로 동시에 두 명이 들어오면?

- 기존에는 `HSET`으로 덮어써서, 뒤에 들어온 사람이 나가면 **앞사람까지 사라졌습니다.**
- **`HSETNX`(putIfAbsent)** 로 바꿔 Redis 명령 하나로 "없을 때만 저장"을 처리했습니다. 동시에 들어와도 한 명만 성공하고, 나머지는 `NICKNAME_TAKEN` 에러를 받습니다.
- `HEXISTS` 후 `HSET`처럼 두 번 나누면 그 사이에 다른 요청이 끼어들 수 있어서 쓰지 않았습니다.

### Q7. Lua Script는 왜, 어디에 썼나요?

- Redis 쓰기를 100ms마다 모아서 하도록 바꾸자 새로운 경쟁 조건이 생겼습니다. **flush가 위치를 꺼낸 직후 플레이어가 퇴장(HDEL)하면, flush의 HSET이 그 플레이어를 되살리는** 문제입니다.
- "아직 방에 있으면(HEXISTS) 저장(HSET)"을 **Lua Script 하나로 원자적으로** 실행해 해결했습니다. 방 하나의 모든 변경을 스크립트 1회, 즉 네트워크 왕복 1회로 처리하는 효과도 있습니다.
- **주의한 점**: Lua 인자는 문자열이라, RedisTemplate의 해시 값 직렬화기로 미리 JSON을 만들어 넘겼습니다. 일반 HSET 값과 형식이 달라지면 읽을 때 역직렬화가 깨지기 때문입니다. 이것은 실제 Redis 테스트로 검증했습니다.

## Redis / 설계

### Q8. 이동할 때마다 Redis에 저장하지 않으면 데이터가 유실되지 않나요?

- 위치는 **최신 값 하나만 의미가 있습니다.** 100ms 안에 여러 번 움직이면 마지막 값만 저장해도 손실이 없습니다.
- 서버가 죽으면 마지막 100ms의 위치가 유실됩니다. 하지만 그때는 **WebSocket 세션도 모두 끊기므로** 그 위치를 쓸 일이 없습니다.
- 새 입장자에게 SYNC를 보낼 때는 **Redis 값 위에 아직 저장 안 된 최신 위치를 덮어써서** 보냅니다. 그래서 새 입장자가 보는 위치도 정확합니다.
- 효과: 10명이 20Hz로 움직일 때 Redis 호출이 **초당 200회 → 방당 초당 최대 10회**로 줄었고, 위치 전달 경로에서 Redis 대기가 사라졌습니다.

### Q9. 서버가 갑자기 죽으면 Redis에 남은 플레이어는?

- `SessionDisconnectEvent`가 오지 않아 **유령 플레이어**가 남습니다.
- Simple Broker는 세션을 서버 메모리에만 갖고 있으므로, **서버가 새로 뜬 시점에 Redis에 있는 플레이어는 전부 유령**입니다. 그래서 `ApplicationReadyEvent`에서 `SCAN room:*`로 찾아 삭제합니다. `KEYS`는 Redis를 블로킹하므로 쓰지 않았습니다.
- **한계**: 서버가 여러 대면 다른 서버의 정상 플레이어까지 지웁니다. 그때는 플레이어별 TTL + Heartbeat 갱신으로 바꿔야 합니다.

### Q10. 서버를 여러 대로 늘리면 지금 구조로 되나요?

- **안 됩니다.** Spring의 Simple Broker는 **서버 메모리 안에서만** 메시지를 전달합니다. A 서버에 붙은 사람의 이동이 B 서버에 붙은 사람에게 가지 않습니다. Redis를 공유해도 메시지 중계는 해결되지 않습니다.
- RabbitMQ 같은 외부 브로커를 **STOMP Broker Relay**로 붙이거나, Redis Pub/Sub로 서버 간 메시지를 중계해야 합니다. 유령 정리 방식도 함께 바꿔야 합니다.

### Q11. 클라이언트가 보낸 `playerId`, `roomId`를 쓰면 안 되는 이유는?

- 실제로 프론트엔드가 `roomId`를 보내지 않아 **`room:null` 키**가 생겼습니다. 또 `playerId`를 믿으면 **다른 사람의 캐릭터를 움직이는 요청**도 처리됩니다.
- 입장할 때 세션 속성에 `nickname`, `roomId`, `role`을 저장하고, 이후에는 **서버가 아는 세션 정보로만** 판단하도록 바꿨습니다.

### Q12. 로그인이 없는데 특정 사용자에게만 메시지를 어떻게 보냈나요?

- `convertAndSendToUser`는 기본적으로 Principal 기준이라, 로그인이 없으면 메시지가 **조용히 버려졌습니다.**
- 메시지 헤더에 세션 ID를 넣어 보내면 Principal 없이도 그 세션으로 전달됩니다. 클라이언트는 `/user/queue/sync`만 구독하면 됩니다.
- 이전에 썼던 `/topic/private/{nickname}`은 **누구나 구독할 수 있어서** 비공개가 아니었습니다.

## 협업 / 태도

### Q13. 가장 기억에 남는 실패는?

- 동기화 필드를 추가하면서 Controller를 한 번에 재설계했습니다(`bb3b885`). 엔드포인트, 토픽 경로, 저장소(Redis → 메모리 Map)를 동시에 바꿨습니다. 그 결과 **클라이언트와 경로가 어긋나 메시지가 아예 오가지 않았고**, 퇴장 처리는 Redis를 보는데 Controller는 메모리를 봐서 **저장소가 둘로 갈라졌습니다.**
- 다음 커밋에서 **동작하던 구조로 되돌리고**(`f8cefed`), 기능을 하나씩 다시 추가했습니다.
- 이후로는 **클라이언트–서버 계약을 먼저 문서로 고정**하고([메시지 계약 명세](./message-protocol.md)), 그 계약을 통합 테스트로 확인하는 방식으로 작업했습니다.

### Q14. 간헐적으로 실패하는 테스트가 있으면 어떻게 하나요?

- `sleep`을 늘려 덮지 않고, **실패 순간의 상태를 출력해 원인부터 확정**합니다. 이 프로젝트에서도 대기를 넣으면 통과했지만, 실패 시점의 저장값을 찍어 보니 **순서 역전**이라는 실제 버그였습니다.
